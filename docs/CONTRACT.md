# Veedor — build contract

Single source of truth for everyone working on this repository tonight. If something here
conflicts with your brief, this file wins. Do not change another owner's directory.

## Product in one paragraph

Veedor is an open risk radar for public procurement in Ecuador. It ingests SERCOP's open
contracting data, computes transparent red-flag indicators per process, cross-checks awarded
suppliers against public registries (SRI, Superintendencia de Compañías), ranks processes by a
risk score, and produces an evidence dossier per alert. Every statement in a dossier must be
traceable to a field in the data. **Veedor reports risk indicators, never accusations.**

## Non-negotiable rules

1. **No invented data.** No made-up numbers, URLs, legal articles, company facts, thresholds or
   benchmark results — in code, tests, docs or UI. If a fact is unknown, the field is `null`
   and the UI says "no disponible".
2. **Grounding.** Any text shown to a user about a real process or supplier is either rendered
   from structured facts by a deterministic template, or produced by an LLM and then checked by
   the grounding verifier (see "Dossier"). Unverified LLM text is never stored or displayed.
3. **Wording.** Use "señal de riesgo", "indicador", "atípico". Never "corrupto", "fraude",
   "irregular", "culpable", or anything that asserts wrongdoing.
4. **People.** Natural persons are not named in the UI or API by default. A RUC whose third
   digit is `0`–`5` belongs to a natural person: expose `supplier_kind = "natural_person"`,
   mask the name as `"Persona natural"` and the RUC as first 4 digits + `*********`. Companies
   (third digit `9`) and public entities (third digit `6`) are shown normally.
   Internal tables keep the real values; masking happens at the API boundary.
5. **Languages.** Code, comments, identifiers, docs, commit messages: English. User-facing UI
   copy and dossier text: neutral, professional Spanish (no regional slang).
6. **No secrets** in the repo. Do not create or edit any `.env*` file (the environment blocks them). Document variables in `docs/CONFIGURATION.md`; every setting must have a safe default for local development.
7. **Do not run `git init`, `git add`, `git commit` or push.** The orchestrator handles git.
   No AI attribution anywhere (no "generated by", no co-author lines).
8. Shell tools: `rg`, `fd`, `bat`, `sd`, `eza` (not grep/find/cat/sed/ls).
9. Tests must not hit the network or need the real data lake; use small synthetic fixtures.
   Real-data checks are separate scripts/commands, reported honestly.

## Architecture (mirrors the team's previous FastAPI projects)

```

  core/            settings (pydantic-settings), paths, logging, errors
  domain/          pure logic, no I/O, no framework imports
    signals/       one module per indicator + registry + scoring
    dossier/       evidence pack model, templates, grounding verifier
  use_cases/       application services orchestrating domain + ports
  infrastructure/
    ocds/          SERCOP bulk flattening (DONE: flatten.py)
    lake/          DuckDB access to Parquet tables and marts

    db/            PostgreSQL (SQLAlchemy 2 + Alembic): dossiers, reviews, embeddings
    llm/           chat-model provider abstraction
    mcp/           optional EcuDataMCP client
  agents/
    investigator/  LangGraph graph: nodes/, prompts/, state
  api/v1/          FastAPI routers
  schemas/         Pydantic API schemas
  cli.py           Typer app (`veedor ...`)
tests/             mirrors src layout; fixtures under tests/fixtures/
web/               Next.js dashboard
```

Dependency rule: `domain` imports nothing from the other layers. `use_cases` depends on
`domain` and on ports (Protocols) defined next to the use case. `infrastructure` implements
ports. `api` and `cli` only call use cases.

Tooling: Python 3.12, `uv`, ruff (line length 110), pytest. Add dependencies with
`uv add <pkg>` (the project already has duckdb, pyarrow, orjson, pydantic, pydantic-settings,
typer, fastapi, uvicorn, httpx). Type hints everywhere. Small functions, no dead code.

## Data lake (Parquet under `data/lake/`, git-ignored)

Already built from 2,251,027 real processes (2015 – Nov 2026).

`processes.parquet` — one row per process (`ocid` unique):
`ocid, process_code, release_date, year, buyer_id, buyer_ruc, buyer_name, buyer_region,
buyer_locality, method, method_group, category, status, description, budget, budget_source,
tender_start, tender_end, enquiry_start, enquiry_end, award_period_start, award_period_end,
n_tenderers, n_tenderers_listed, n_bids, n_enquiries, n_awards, award_total,
first_award_date, date_signed, main_cpc, main_cpc_description, has_tender_block`

- Dates are ISO-8601 strings with offset (e.g. `2023-08-02T10:00:00-05:00`); cast in SQL.
- `method_group` ∈ `catalogue | competitive | direct | other | no_tender_block | unknown`.
- Verified coverage: competitive (267,037 rows) has `n_tenderers` in 99.4 %, budget in 100 %,
  award in 95.5 %, `tender_end` in 31 % (present for Menor Cuantía, Cotización, Licitación;
  absent for Subasta Inversa Electrónica). Catalogue rows (1.86 M) have no bidder data.

`tenderers.parquet` — `ocid, supplier_id, supplier_ruc, supplier_name` (distinct per process).

`awards.parquet` — `ocid, award_id, award_date, supplier_id, supplier_ruc, supplier_name,
amount` (`amount` is null when one award lists several suppliers).

Registry tables (owner: registries):
- `suppliers_sri.parquet` — `ruc, legal_name, status, taxpayer_type, activity_start_date,
  suspension_date, restart_date, ciiu_code, activity, province, source_file`
- `ghost_companies.parquet` — SRI "empresas fantasmas" list if obtainable: `ruc, legal_name,
  resolution, publication_date, source_file` (absent file = dataset not obtained)
- `companies_supercias.parquet` — `ruc, expediente, legal_name, company_type, province` plus,
  if available from the ranking file, yearly financials in
  `company_financials.parquet` — `ruc, year, revenue, assets, equity, employees`
  (only columns that really exist in the source; document the mapping).

Marts (owner: signals), written to `data/marts/`:
- `process_signals.parquet` — `ocid, signal_code, value (double), threshold (double),
  evidence_json (string)`; one row per fired signal.
- `process_scores.parquet` — `ocid, risk_score (0–100), n_signals, signal_codes (list<string>),
  anomaly_score (double, nullable), award_total, year, buyer_ruc, buyer_name, method,
  winner_ruc, winner_name, winner_kind`
- `supplier_profiles.parquet` — `ruc, name, kind, n_processes, n_wins, total_awarded,
  first_award_date, last_award_date, n_buyers, top_buyer_ruc, top_buyer_share,
  single_bidder_wins, mean_risk_score`

## Signals v1

Each signal is a pure, documented rule with a code, a Spanish label, the exact fields it uses,
its threshold and how the threshold was derived. Thresholds that are statistical must be
computed from the data (percentiles per method and year), not hard-coded guesses.

| code | idea | scope |
|---|---|---|
| `SINGLE_BIDDER` | exactly one tenderer | competitive |
| `SHORT_TENDER_WINDOW` | tender_end − tender_start below the 5th percentile of its method-year | rows with both dates |
| `LOW_SAVING` | award_total / budget at or above the 95th percentile of its method-year, and ≥ 0.99 | competitive with budget |
| `NEW_SUPPLIER` | winner's SRI activity start < 180 days before first award date | awards with registry match |
| `SUPPLIER_NOT_ACTIVE` | winner's current SRI status is not active (caveat: current status, not status at award time) | registry match |
| `GHOST_COMPANY_LIST` | winner appears in SRI's published ghost-company list | if dataset obtained |
| `BUYER_CONCENTRATION` | winner received ≥ 30 % of the buyer's awarded amount that year, buyer-year total ≥ USD 100k, ≥ 3 awards | all non-catalogue |
| `REPEATED_DIRECT_AWARDS` | same buyer + same supplier + same CPC 5-digit prefix, ≥ 3 direct-group processes within 90 days | direct |
| `RECURRING_COBIDDERS` | winner and the same losing bidder met in ≥ 5 competitive processes of the same buyer | competitive |
| `CONTRACT_VS_COMPANY_SIZE` | award_total > 3 × company's latest reported annual revenue | if financials obtained |

Score: weighted sum of fired signals, capped at 100; weights live in one config module and are
documented in METHODOLOGY.md with their rationale and the statement that they are judgement
calls pending calibration. `anomaly_score`: Isolation Forest (scikit-learn) on numeric process
features, reported separately — it never changes `risk_score`.

## Dossier

`EvidencePack` (pydantic): process facts, fired signals with their evidence, winner registry
facts, buyer–supplier history, comparable statistics, and `sources` (dataset name, licence,
retrieval date, record id). `Dossier`: `ocid, generated_at, mode ("template" | "llm"),
summary_es, sections[], sources[], grounding_report`.

Grounding verifier (pure function, heavily tested): extracts every number, date, RUC, process
code and proper name from generated text and checks each against the EvidencePack values
(with explicit, documented normalisation for number formats). Any unsupported token ⇒ the text
is rejected. The LLM gets one retry with the rejected tokens listed; then the system falls
back to the deterministic template. The dossier records which path was taken.

LLM is optional: with no API key the system runs fully in `template` mode.

## API (FastAPI, prefix `/api/v1`)

- `GET /health`
- `GET /stats` → totals, coverage, signal counts by code, last data date
- `GET /processes?year=&method=&buyer_ruc=&signal=&min_score=&q=&page=&page_size=&sort=`
  → paginated rows from `process_scores`
- `GET /processes/{ocid}` → process facts + fired signals (with evidence) + winner profile
- `GET /processes/{ocid}/dossier` → dossier (generated on demand in template mode, cached)
- `GET /suppliers/{ruc}` → supplier profile, registry facts, recent processes
- `GET /buyers/{ruc}` → buyer summary, top suppliers, signal mix
- `GET /signals` → catalogue of signals (code, label, description, threshold rule)
- `POST /processes/{ocid}/reviews` and `GET /processes/{ocid}/reviews` → human review
  (`status ∈ pending | confirmed_signal | dismissed`, `note`), stored in PostgreSQL

All list responses: `{ "items": [...], "page": 1, "page_size": 25, "total": 123 }`.
Masking rule for natural persons applies to every response.
CORS: allow `http://localhost:3000`.
